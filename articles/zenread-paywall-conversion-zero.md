## はじめに

個人開発でChrome拡張機能を36本CWSで公開しています（2026年6月時点）。その中の一本「ZenRead」というリーダーモード拡張で、ある時期からPro機能を用意し、popupとリーダー画面でPro案内（いわゆるpaywall）を表示するようにしました。

直近30日のデータを集計したところ、こんな数字が出ました。

| 指標 | ZenRead |
|------|---------|
| paywall表示回数 | **26回** |
| upgrade（購入導線）クリック | **0回** |
| 転換率 | **0.0%** |

26回見せて、ゼロ。一回もクリックされませんでした。

同じ社内の別拡張「ReadMark」（読書の進捗管理）を比較に出すと、こちらは paywall 223回 → クリック 65回で **転換率 29.1%**。同じ「読書系」の拡張なのに、片や独占級の29%、片やゼロ。

何が違ったのか。実データを晒しながら、フリーミアム設計でやりがちな落とし穴を整理します。

## ZenRead とは何か

ZenRead は Chrome 拡張機能のリーダーモードです。広告・サイドバー・SNSボタンなどのノイズを除去し、本文だけのクリーンな表示に切り替えます。テキスト抽出には Mozilla の Readability.js を採用しているので、Firefox のリーダーモードと同等の精度が出ます。

無料機能：
- リーダーモード本体
- バイオニックテキスト
- TTS（読み上げ）
- テーマ・フォントの基本カスタマイズ

Pro機能：
- ストリーク（連続日数の計測）
- ストリーク・フリーズ（連続日数を守るアイテム）
- Wrapped（年間サマリーレポート）
- ハイライト保存などの記録系

popupを開いたとき、Reader画面に入ったときに「Upgrade to Pro」のバナーが出ます。これが30日で26回表示されました。

## 転換ゼロという数字を直視する

| 日付 | paywall_shown | upgrade_clicked |
|------|--------------|-----------------|
| 4/22 | 9 | 0 |
| 4/30 | 5 | 0 |
| 4/02 | 8 | 0 |
| 4/20 | 2 | 0 |
| その他 | 2 | 0 |

クリック1個が出れば「サンプル数の問題」と言えますが、ゼロは「サンプル数の問題ではない」明白なシグナルです。同期間に first_opens（初回起動）は 137件ありました。新規ユーザーが100人以上来て、26人がPro導線を見て、誰一人として「もっと知りたい」と思わなかった。

ここから目を逸らしてはいけない、と思いました。

## 失敗の仮説４つ

何が悪かったのか。コードを読み返し、ReadMark（成功側）と比較し、自分の中で４つの仮説を立てました。

### 仮説1：タイミングが早すぎた

ZenRead の paywall は popup を開いた瞬間と、Reader 画面を開いた直後に発火します。

```typescript
// popup/Popup.tsx
useEffect(() => {
  if (!isPro) trackPaywallShown('popup_upgrade');
}, [isPro]);

// reader/Reader.tsx
useEffect(() => {
  if (!isPro) {
    trackPaywallShown(isTrialActive ? 'trial_banner' : 'upgrade_banner');
  }
}, [isPro, isTrialActive]);
```

ユーザーがリーダーモードを **使い始める前** に、もう Pro の話をしている。これは順番が逆です。本来は「価値を体験してから課金訴求」のはずなのに、価値の体験前に値札を見せている。

ReadMark の paywall は「読書を進めて記録が溜まってから」「機能制限にぶつかってから」発火するように設計されています。ユーザーは既に「これは便利だ」と思った後で課金導線に出会う。これがそのまま転換率の差として出ました。

### 仮説2：価値訴求の弱さ

ZenRead の Pro機能は「ストリーク」「Wrapped」「フリーズ」など、習慣化サポート系の機能群です。これは便利な機能ですが、**「リーダーモードを使いに来た人」にとっては付随的** です。

ユーザーは「広告だらけのページから本文だけ抽出したい」という1点突破でインストールしてくれている。彼らに「31日連続で記事を読むと特典が」と言っても、「いや、そういうのはいいから……」となる。文脈が噛み合っていない。

### 仮説3：解決済みの問題に再課金請求している

ZenRead の無料版だけで「広告除去」「クリーン表示」「TTS」「フォント変更」が一通り使えてしまいます。コア体験は無料で完結している。

このうえで Pro を出すには、無料版で **わざと不便** にする（リバーストライアル）か、Pro でしか解決できない別の問題を提示する必要があります。ZenRead はどちらもできていなかった。「無料で十分満足、Pro は別にいいかな」となる構造。

### 仮説4：ターゲットと Pro 価値の不一致

リーダーモードを欲しがる層は「集中して読みたいが、ノイズで気が散る」人です。彼らがお金を払いたいのは「より深い集中」「より速い読書」「読了の証拠」あたり。

一方、ZenRead が用意した Pro は **習慣化トラッカー** に寄っています。これは Duolingo 的な「楽しく続ける」体験を作る機能群。読書の真剣勢ではなく「続けるのが目的」になっている人向け。

ターゲット（深く読みたい人）と Pro 価値（楽しく続けたい人向け機能）が、ずれていました。

## 改善案３パターン

ここまで分析した上で、次の打ち手を３つ用意しました。どれを採用するかはまだ決めていません。データを取って判断します。

### A案：paywall を消して完全フリーに戻す

転換ゼロなら、paywall は **ノイズでしかない** 。これを消すとリテンションは確実に上がります（不快な広告がなくなる）。代わりにユーザー基盤を広げて、別の収益化（クロスプロモ・寄付・別拡張への送客）で回収する戦略。

メリット：迷いがなくなる、CWS レビューで叩かれない、レビュー★が安定する
デメリット：直接的なPro収益はゼロ確定

### B案：トリガーを変える

paywall の発火条件を「使い始めた瞬間」から「価値体験後」に変える。具体的には：

- 5記事をリーダーモードで読了した後
- TTSを10分以上連続使用した後
- 7日連続で利用した後

ReadMark がこれに近い設計で、転換率29%を出しています。実装コストは小さく、A/Bテストで比較できる。

### C案：Pro機能を再設計する

「習慣化トラッカー」を捨てて、**読書の質** に寄せた Pro を作り直す：

- 長文記事の自動要約（AI連携）
- 複数記事の横断検索
- ハイライト＋メモのクロスデバイス同期
- 読了済み記事のローカル全文検索

これはターゲット（深く読みたい人）の文脈に合っている。ただし開発コストは大きく、Pro 機能を一旦廃止してから作り直す形になる。

## データドリブンな個人開発の意義

「失敗から学ぶ」は手垢のついた言葉ですが、実際にやるには **数字を見て認める作業** が必要です。

paywall_shown=26 / upgrade_clicked=0 という数字を見ずに、「機能はちゃんと作った」「UIも整えた」「いつかは伸びる」と希望的観測でいると、いつまでも改善できません。

逆に数字を直視すると、26と0だけで仮説が4つ出てきて、改善案も3つ出ます。「とりあえず作る → 計測する → 仮説を立てる → 直す → また計測する」のループに、ようやく入れます。

個人開発で売上を作るのに必要なのは、最初から正解を当てる才能ではなく、**間違いを早く見つけて直すスピード** だと改めて思いました。リリースして転換ゼロでもいい。それが3週間で気付ければ、また直せます。

3週間気付かないままユーザー数が減っていく方が、ずっと痛い。
