## 応募したら全部「Ghost Job」だった

転職活動中、Indeed と LinkedIn を毎日スクロールして「これだ」と思った求人に 30 件応募した結果、返信が来たのはわずか 2 件。そのうち 1 件は「すでに採用が決まっています」という定型文でした。

調べてみると、求人広告の世界には **Ghost Job（幽霊求人）** という概念があるそうです。米 Resume Builder の 2024 年調査によれば、採用担当者の **約 4 割が「現在埋める予定のない求人を出している」** と回答しています。理由は「人材プールを溜めておきたい」「会社が成長している印象を与えたい」「既存社員にプレッシャーをかけたい」など、応募者にとっては時間泥棒以外の何物でもありません。

そこで「**応募する前に、その求人がアクティブかどうかを 1 秒で判定したい**」と思い、Chrome 拡張 `GhostJob` を作りました。LLM は使っていません。シンプルなヒューリスティクスだけで、Indeed・LinkedIn・Glassdoor の求人カードに「👻 Likely Ghost · 75」のようなバッジを差し込むだけの拡張です。

本記事では、その **スコアリングロジック** と **3 サイトの DOM 差異の吸収** を解説します。AI を使わず、ローカル DOM 解析だけで「応募する価値がある求人かどうか」を可視化する設計の参考になれば嬉しいです。

## Ghost Job の検出指標

求人募集が「幽霊」かどうかを完璧に判定する方法はありません。しかし、過去の求人サイトの研究や Reddit r/jobs の口コミからいくつかの傾向が見えてきます。

| 指標 | Ghost に多い傾向 |
| --- | --- |
| 掲載期間 | 30 日超で再掲載されつづけている |
| 募集要項の具体性 | 「やる気のある方」「コミュ力重視」など漠然 |
| 文字数 | 200 字以下の薄い JD（Job Description） |
| 重複掲載 | 同社が似た文面で 5 件以上掲載 |
| 連絡先 | 「採用担当」のみで担当者名なし |

`GhostJob` ではこのうち **掲載期間・募集要項の具体性・文字数・同社内の類似投稿数** を採用しました。「連絡先」は LinkedIn 以外で取得が難しく、誤判定のもとになるため除外しています。

これらの指標を選んだ理由はシンプルで、**DOM だけで安定して取れる**から。求人サイトは 3 か月単位でレイアウトを変えてきますが、「タイトル・会社名・掲載日・本文の文字数」は意味的に必須要素なので、セレクタが変わっても探せば必ず見つかります。逆に「面接実施回数」「過去 3 年の採用者数」のような企業の内部情報を頼ると、サイト側 API が変わった瞬間に拡張が壊れます。

## スコアリングロジック（コア実装）

スコアは **0〜100 で正規化** し、61 以上を「Likely Ghost」と判定します。実装は `lib/ghost-scorer.ts` に閉じています。

```ts
function daysScore(daysSincePosted: number): number {
  if (daysSincePosted >= 90) return 60;
  if (daysSincePosted >= 60) return 40;
  if (daysSincePosted >= 30) return 20;
  if (daysSincePosted >= 14) return 10;
  return 0;
}

function duplicateScore(similarPostings: number): number {
  if (similarPostings >= 5) return 20;
  if (similarPostings >= 3) return 15;
  if (similarPostings >= 2) return 8;
  return 0;
}

function vaguenessScore(descLen: number, hasSpec: boolean): number {
  let score = 0;
  if (descLen < 200) score += 15;
  else if (descLen < 400) score += 8;
  if (!hasSpec) score += 10;
  return score;
}

export function calculateGhostScore(f: GhostFactors): number {
  let score = 0;
  score += daysScore(f.daysSincePosted);
  score += duplicateScore(f.similarPostings);
  score += vaguenessScore(f.descriptionLength, f.hasSpecificRequirements);
  return Math.min(score, 100);
}
```

### 配点設計の意図

- **掲載期間（最大 60 点）** … 最重要シグナル。30 日超は「アクティブな採用ではない」可能性が一気に上がる。90 日超は単独で「Caution（黄色）」域に達する重みにした。
- **重複掲載（最大 20 点）** … 同社が似た JD を量産している場合、人材プール目的の可能性が高い。
- **漠然さ（最大 25 点）** … 文字数 200 未満 + 具体要件なしで合計 25 点。実在の求人は「3 年以上の経験」「React 必須」など必ずスキル要件が書かれる。

### 「具体的な要件」の判定

`checkHasSpecificRequirements` では正規表現で **本気の求人らしいキーワード** が含まれているかを見ます。

```ts
const specificPatterns = [
  /\d+\+?\s*years?\s*(of\s*)?(experience|exp)/i,
  /bachelor'?s?|master'?s?|phd|degree/i,
  /proficient\s+in\s+\w+/i,
  /experience\s+with\s+\w+/i,
  /certification/i,
  /\breact\b|\bpython\b|\bjava\b|\btypescript\b|\bsql\b|\baws\b/i,
];
return specificPatterns.some(p => p.test(description));
```

「○年以上の経験」「学位」「特定スタックの言及」のいずれかが入っていれば `true`。これだけで Ghost Job 判定の精度が体感で 1 段階上がります。

### 日付パーサ

DOM のテキストから掲載日数を抽出する処理は地味に厄介です。「Posted 3 days ago」「2 weeks ago」「30+ days ago」など表記がバラバラだから。

```ts
export function parseDaysAgo(text: string): number {
  const t = text.toLowerCase().trim();
  if (/today|just posted|now/.test(t)) return 0;
  if (/(\d+)\s*hour/.test(t)) return 0;
  const day = t.match(/(\d+)\s*day/);
  if (day) return parseInt(day[1], 10);
  const week = t.match(/(\d+)\s*week/);
  if (week) return parseInt(week[1], 10) * 7;
  const month = t.match(/(\d+)\s*month/);
  if (month) return parseInt(month[1], 10) * 30;
  if (/30\+/.test(t)) return 35; // "30+ days ago" を 35 日とみなす
  return 0;
}
```

`30+ days ago` という曖昧表記は「最低 30 日」なので、安全側に倒して 35 日として扱うのがポイントです。

## 3 サイトの DOM 差異をどう吸収したか

Indeed / LinkedIn / Glassdoor は求人カードの構造が全部違います。content script では **hostname で分岐 → セレクタ表だけ差し替える** というシンプルな実装に落とし込みました。

```ts
if (hostname.includes('indeed')) {
  cards = document.querySelectorAll('.job_seen_beacon:not([data-ghostjob-scored])');
} else if (hostname.includes('linkedin')) {
  cards = document.querySelectorAll('.job-card-container:not([data-ghostjob-scored])');
} else if (hostname.includes('glassdoor')) {
  cards = document.querySelectorAll('[data-test="jobListing"]:not([data-ghostjob-scored])');
}
```

ポイントは 2 つ。

1. **`:not([data-ghostjob-scored])` で多重処理を防ぐ** … 各サイトとも MutationObserver で無限スクロールを処理するため、処理済みカードに属性を付けて二重スコアを防止する。
2. **クラス名は属性セレクタで逃げる** … LinkedIn は `.artdeco-entity-lockup__title` などビルドハッシュ風のクラスを使うが、`[class*="title"]` のような部分一致セレクタを併用すると DOM 微調整への耐性が上がる。

LinkedIn の `time` 要素は `datetime` 属性に ISO 日付が入っているので、テキスト解析より優先します。

```ts
const postedText = dateEl?.getAttribute('datetime')
  ?? dateEl?.textContent?.trim()
  ?? '';
```

### 実際のスコアリング例

実装した結果、以下のような出力になります（Indeed の検索結果ページで観測した実例）。

| 求人タイトル | 掲載日数 | JD 文字数 | スキル要件 | スコア | 判定 |
| --- | ---: | ---: | --- | ---: | --- |
| Senior React Developer | 5 | 1820 | あり | 0 | Likely Real |
| Sales Representative | 45 | 320 | なし | 38 | Caution |
| Marketing Coordinator | 90 | 180 | なし | 85 | Likely Ghost |
| DevOps Engineer | 60 | 950 | あり | 40 | Caution |

掲載日数が 90 日を超えて JD が薄い 3 番目の求人が、確かに「人材プール目的」の典型に見えます。逆に 4 番目は判定が割れる典型例で、「60 日経過しているがスキル要件が具体的」なため Caution に踏みとどまっています。閾値の境界線を体感できる UI として機能してくれているようです。

## 限界と「やらなかった判断」

スコアリングロジックは **誤判定（false positive）が出るほど信頼を失う** ので、以下は意図的に実装を見送りました。

- ❌ **企業の財務データ参照** … 求人ページから Yahoo Finance を裏で叩いて「最近大量解雇した会社か」を見る案。クロスオリジン制約と速度のトレードオフで断念。
- ❌ **応募者数 vs 採用人数比** … LinkedIn の「100+ applicants」を使う案。スタートアップの本気の求人ほど応募が殺到するため、Ghost 判定に直結しない。
- ❌ **LLM での JD 解析** … API コストが拡張ユーザーに乗ってしまう。ヒューリスティクスでも体感の精度は十分。

代わりに **「Caution（黄色）」を広めに取り、断定を避ける** UX にしました。スコア 31〜60 は「気になるなら詳細を確認しよう」というシグナル。判断はユーザーに委ねます。

```ts
function getGhostLevel(score: number) {
  if (score <= 30) return { label: 'Likely Real',  color: '#16a34a' }; // green
  if (score <= 60) return { label: 'Caution',      color: '#d97706' }; // amber
  return                  { label: 'Likely Ghost', color: '#dc2626' }; // red
}
```

「断定するスコアは 100 点中 61 点から」という閾値設計は、**応募者の機会損失（Type II error）と、本物の求人を取り逃すリスク（Type I error）のバランス**から決めました。アルバイトや短期契約の求人だと「30 日経過 + 短い JD」が普通に発生するため、ここで Ghost 判定すると怒られます。実際にベータユーザーから「フリーランス系のチープな案件で誤判定が多い」というフィードバックをもらい、Type I を抑える方向に重みを再調整しています。

### 観測された誤判定パターン

公開後 1 ヶ月のフィードバックで、以下の偽陽性・偽陰性が出やすいと分かりました。

- **偽陽性**：政府・自治体の公務員系求人（JD は短いが本気で募集している）
- **偽陽性**：日本語の Indeed 求人（specificPatterns が英語前提のため、日本語 JD ではほぼ全件「漠然」判定）
- **偽陰性**：「3 年以上の経験」とテンプレで書きつつ採用予定がない大手の Ghost Job

特に日本語 JD は次のリリースで `^[ぁ-んァ-ン一-龥]+$` 検出を入れて点数を緩める予定です。「ローカライズ無視で英語前提のレギュレックス」は、グローバル対応を後回しにすると必ず痛い目を見るパターンの教科書のような事例でした。
